# yulstar — "ai가 출시된 이후로 개발자들의 개발의 양이 정말로 많아졌을까?"

## 팀원
- 20119 이나율
- 20508 김한별

## 질문
"ai가 출시된 이후로 개발자들의 개발의 양과 질이 정말로 높아졌을까?"

## 왜 이 주제인가 (팀이 씁니다)
두 명 모두 ai를 즐겨 씁니다. ai로 바이브코딩하는 것을 좋아하는 둘이 뭉쳐, 과연 실제 개발자들도 바이브코딩을 즐겨 쓸 지에 대해 탐구하게 되었습니다.
- 20119 이나율: 평소 AI를 활용해 코딩하는 것을 좋아하고, AI로 바이브 코딩을 했을 때 제가 만들지 못하는 것을 척척 만드는 것에 감탄했었습니다. 실제 개발자들도 AI가 코딩을 도와주면 개발 속도나 결과물의 질이 실제로 좋아지는지 궁금했습니다. 그래서 실제 개발자들의 GitHub 커밋 데이터를 통해 AI 활용 여부와 개발 작업의 종류 사이에 어떤 관계가 있는지 알아보고 싶었습니다.
- 20508 김한별: - 저도 AI가 등장한 이후 텍스트 코딩을 시작했기 때문에, 실제로 AI의 도입이 개발자들의 개발량 증가로 이어졌을까 궁금해졌습니다. GitHub 커밋 데이터를 활용해 AI가 작성한 커밋과 인간이 작성한 커밋, AI의 도움을 받은 커밋 등을 비교하고, AI 활용이 실제 개발 활동에 어떤 영향을 미치는지 알아보고자 했습니다.
## 데이터
- 출처: Who Writes AI Code? (kaggle). 2026년 10월 1일에 수집 된 118개 GitHub 저장소의 공개 Git 히스토리 repos.csv(커밋 메타데이터만 포함, 소스 코드 제외)를 기반으로 구축된 데이터베이스, 2026-10-22 접근
- 기간·행 수·열 수: 1,358,007행 × 16열
- 사용한 열: author_type(사용자가 인간인지 ai인지), author_org(사용자가 개인인지 기업인지), ai_assisted(ai로 도움을 받았는지), ai_tool(도움을 받은 ai의 종류), ai_model(ai의 버전), commit_type(한 작업의 종류)
- 개인 단위 정보 없음 확인: 사용자에 대한 정보에 관한 열에 개인정보가 있다. 깃허브 프로필이 들어간 데이터가 있으므로 전처리 과정에서 삭제할 예정이다.

## 방법

생성형 AI 대중화 전후의 개발 활동을 비교하기 위해 월별 커밋 수와 작업 종류별 비율을 분석한다. 회귀 분석으로 시간에 따른 커밋 수의 변화도 살펴본다.

분석 과정:

1. **데이터 수집:** GitHub 커밋 데이터를 불러와 커밋 날짜, 저장소, AI 활용 표시, 작업 종류 등 분석에 필요한 열을 확인한다.
2. **변수 선택:** 커밋 날짜와 저장소 식별 정보를 중심으로 월별 커밋 수를 계산하고, `commit_type`으로 작업 구성을 파악한다. AI 관련 변수는 추가 비교에 활용한다.
3. **전처리:** 중복과 날짜 누락을 확인하고, 개인을 식별할 수 있는 정보는 분석에서 제외한다. 생성형 AI 대중화의 기준 시점을 `[기준 연월]`로 정하고, 동일한 저장소의 전후 각각 `[ ]개월`을 비교한다. 수집 범위 안에서 실제 커밋이 없었던 달과 데이터가 누락된 달을 구분한다.
4. **분할:** 회귀 모델을 평가할 때는 시간순으로 앞의 80%를 학습용, 뒤의 20%를 평가용으로 사용한다.
5. **기준선:** 학습 기간의 월평균 커밋 수를 모든 평가 월에 동일하게 예측하는 모델을 기준선으로 사용한다.
6. **후보 모델 비교:** 시간 변수만 사용하는 선형회귀와, 시간·AI 대중화 전후·이후 경과 개월을 사용하는 회귀 모델을 비교한다.
7. **선택:** 평가 데이터에서 평균절대오차(MAE)가 낮은 모델을 선택한다.
8. **평가:** 모델의 예측 오차와 함께, AI 대중화 전후 월평균 커밋 수의 변화율과 작업 종류별 비율 차이를 계산한다.
9. **해석:** 전체 결과와 저장소별 결과를 비교해 변화가 여러 저장소에서 공통으로 나타나는지 확인한다.
10. **한계 점검:** 저장소 규모, 프로젝트 성장, AI 활용 표시 누락 등 결과에 영향을 줄 수 있는 요인을 검토한다. 관찰된 전후 차이를 AI의 인과적 효과로 단정하지 않는다.

## 결과 해석

- **사용한 지표와 수치:**  
  비교에 포함된 저장소는 `[ ]개`이다. AI 대중화 이전 월평균 커밋 수는 `[ ]건`, 이후는 `[ ]건`으로, `[ ]%` `[증가/감소]`했다. 선택한 회귀 모델의 MAE는 `[ ]건`이었다.

- **기준선과 비교하면:**  
  기준선 모델의 MAE는 `[ ]건`, 선택한 모델은 `[ ]건`이었다. 선택한 모델의 오차가 기준선보다 `[ ]%` `[작았다/컸다]`.

- **이 결과가 뜻하는 것:**  
  분석 대상 저장소에서는 AI 대중화 이후 커밋 활동량이 `[증가/감소/큰 변화 없음]`하는 모습을 보였다. 다만 커밋 수는 작업을 나누는 방식에도 영향을 받으므로, 이를 개발 생산성의 변화와 동일하게 해석할 수는 없다. 작업 종류별 비율은 개발 활동의 구성을 보여 주며, 코드 품질을 직접 측정하지는 않는다.

- **우리 팀이 찾아낸 것:**

  1. **개발 활동량의 변화**  
     월평균 커밋 수가 `[ ]건`에서 `[ ]건`으로 변했다. 이는 분석 대상에서 기록된 개발 활동량이 달라졌음을 보여 준다. AI가 등장하면 개발량이 반드시 증가할 것이라는 예상과 비교했을 때, 결과는 `[예상과 일치했다/달랐다]`.

  2. **개발 작업 구성의 변화**  
     `[작업 종류]`의 비율이 `[ ]%`에서 `[ ]%`로 `[ ]%포인트` 변했다. 이는 AI 대중화 전후 개발 작업의 구성이 달라졌음을 보여 준다. 모든 작업이 비슷하게 변할 것이라는 예상과 비교하면 `[실제 발견한 차이]`가 있었다.

  3. **저장소마다 다른 변화**  
     분석한 `[ ]개` 저장소 중 커밋 수가 증가한 곳은 `[ ]개`, 감소한 곳은 `[ ]개`였다. 전체 평균과 개별 저장소의 결과가 `[일치했다/달랐다]`. 따라서 전체 평균만으로 모든 프로젝트의 변화를 설명하기는 어렵다.

## 한계

- **이 결과를 해석할 때 주의할 이유:**  
  원본 데이터는 118개 저장소를 대상으로 하므로 GitHub 전체를 대표한다고 보기 어렵다. 전처리 후 분석에 포함한 저장소는 `[ ]개`이며, `[제외 사유]`로 제외한 커밋은 `[ ]건`, 전체의 `[ ]%`였다. 또한 AI 대중화 시점과 각 개발자가 실제 AI를 사용하기 시작한 시점은 다를 수 있다. 개발자 수와 프로젝트 규모 등의 영향을 충분히 통제하지 못했다.

- **품질 평가의 한계:**  
  소스 코드와 테스트 결과가 없어 코드 품질의 향상 여부를 직접 판단할 수 없다. 버그 수정 커밋의 증가는 결함 증가뿐 아니라 유지보수 활동의 증가를 의미할 수도 있다.

- **이 결과를 잘못 쓰면 생길 수 있는 일:**  
  커밋 수가 많다는 이유만으로 개발자의 능력이 높다고 평가하거나, AI 사용이 생산성과 품질을 반드시 향상시킨다고 주장할 수 있다. 이는 개발자의 실제 기여와 프로젝트 특성을 무시한 평가로 이어질 수 있다.

## 더 해 보고 싶은 것

- **교과 연계:**  
  확률과 통계의 평균, 비율, 상관관계와 인과관계 개념을 실제 데이터에 적용하고 싶다. 정보 교과의 데이터 전처리, 시각화, 회귀 모델 평가와도 연결할 수 있다.

- **진로 분야:**  
  소프트웨어 개발과 데이터 분석 분야에 연결해, 개발자의 생산성을 공정하게 측정하는 방법을 탐구하고 싶다. 이후에는 테스트 통과율, 오류 발생률, 코드 검토 결과 등을 추가해 품질도 분석하고 싶다.
